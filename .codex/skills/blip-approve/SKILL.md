# Blip Approve (human-equivalent counted vote)

Use this skill to coordinate the bounded pre-vote continuity loop when explicitly authorized, followed by at most one final counted approval attempt through the protected broker. Independent review, coordinator repair, thread handling, the counted vote, and merge remain distinct operations with separate evidence and credentials.

## Bounded continuity loop before the vote

When `全權處理` applies, run this coordinator-owned loop before evaluating the final vote gates:

1. Bind every round to the named PR and re-read its current base/head tuple. Treat a new head as a new review round; never reuse stale findings, checks, or approval evidence.
2. Preserve exactly one repository policy classification: `mechanical_only`, `focused_semantic`, `risk_scoped_specialists`, or `human_critical`. Never convert `human_critical` into a machine-eligible mode; record the user-authored tuple-bound override separately. Review the current diff with the reviewers allowed by that policy mode. Prefer a read-only reviewer distinct from the fixer when the active workflow requires separation; coordinator self-review is allowed as advisory evidence but must record `reviewer_kind=self_review` separately from the policy classification and never count as the independent or CODEOWNER approval.
3. Classify findings. Only `confirmed + in_scope + fix_now` findings enter repair. Refuted, external, out-of-scope, follow-up, and unverified items stay explicit and are never silently converted into resolved work.
4. The coordinator applies the smallest repair, runs the affected verification gates, and pushes the repaired head. The reviewer and the vote-only helper never fix, push, or receive write credentials.
5. Resolve one GitHub review thread only after its exact finding is fixed on the current head and the matching verification evidence is recorded in a reply or disposition. Immediately before the reply/resolve mutation, re-read the PR head and require the expected head; immediately afterward, re-read both head and thread state. Provider-side thread resolution has no atomic head predicate, so any pre/post drift is reported as `resolution_race`; do not issue a compensating unresolve that could overwrite a new-head actor's legitimate decision. Preserve the evidence reply, treat the thread state as ambiguous, HOLD further resolution/vote mutation, and start a new-head review. Never bulk-resolve, resolve merely to make the unresolved-thread count reach zero, or dismiss a review.
6. Re-review the new head. Continue without another user prompt while each round makes verifiable in-scope progress. Follow the repository evidence-loop limit for the same recurring problem; a repeated failure without new evidence, hypothesis, or method is a real HOLD, not a reason to busy-loop.

Repairable in-scope review findings or check failures return to this loop; they are not additional human-authorization boundaries. Stop only at a genuine fail-closed boundary such as an ambiguous target, unrelated or unsafe write scope, unknown/unclassifiable risk, overlapping user changes that cannot be integrated safely, missing credential or permission, protection drift, or evidence that remains incomplete or stale after a narrow reread. The one live vote is attempted only after the loop reaches a clean exact head and every gate below passes.

2. PR is OPEN, not draft, based on `main`, has no auto-merge request, and repository `allow_auto_merge` is explicitly `false`.
3. All required checks on the exact head are successful. GitHub treats `success`, `skipped`, and `neutral` as successful for ordinary required checks, but `agent-governance` must conclude actual `success` and originate from GitHub Actions App id `15368`.
4. Zero unresolved review threads. Never resolve threads to satisfy this gate.
5. Branch protection intact: approvals=1, require code-owner reviews, dismiss stale reviews, conversation resolution, enforce admins.
6. The applicable risk-proportional review packet is complete and records exactly one policy classification: `mechanical_only`, `focused_semantic`, `risk_scoped_specialists`, or `human_critical`. ```powershell
